# V2 알림 시스템

## 데이터 흐름

회원의 정상 게시·댓글 작성 → 기존 권한 검사 → DB trigger 및 선택 ID 멘션 처리 → private.notifications → private.notification_deliveries → 서버 전용 push-dispatch → 푸시 서비스 순서입니다. 앱 내부 기록과 푸시 전송 트랜잭션을 분리하여 푸시 실패로 알림을 지우지 않습니다.

## 저장 구조

| 테이블                                | 용도                                                                            |
| ------------------------------------- | ------------------------------------------------------------------------------- |
| notifications (기존 확장)             | type, event_key, notice_id, comment_id, important 추가. 기존 행 유지            |
| notification_preferences              | 종류별 알림·전체 푸시·방해 금지·시간대·검색 노출·revision·inbox_revision        |
| push_subscriptions                    | 실제 계정·현재 Auth 세션·기기 이름·Web Push 키. 본인 API에도 키·주소 반환 안 함 |
| post_subscriptions / bookmarks        | 본인 글 구독과 저장. 원본 삭제·탈퇴 시 cascade                                  |
| mentions                              | 작성자·수신자 실제 ID, 게시글/댓글 FK. 익명 작성자 ID를 응답에 추가하지 않음    |
| notification_deliveries               | 알림/기기 unique, 상태·시도 횟수·lease·다음 시도 시각                           |
| push_scheduler_nonces                 | 서명된 스케줄러 요청의 재사용 방지, 10분 후 정리                                |
| notification_delivery_logs            | 시도별 HTTP 결과, 키·주소·본문 기록 안 함                                       |
| sanctions / sanction_appeals (재사용) | 서버 만료 통지 마커 추가, 동일 제재 이의 제기 3회 한도                          |

모두 private + RLS + anon/authenticated 직접 권한 회수입니다. 공개 invoker `schoolpot_v2` → private definer에서 actor_role로 실제 계정·현재 세션·DB 역할을 검사하고 현재 소속과 이용 제한을 다시 검사합니다. 기존 API와 마찬가지로 RLS 정책 없이 직접 접근을 기본 거절하며 전용 함수를 통해서만 접근합니다.

## 생성과 중복 제거

- 댓글 한 건의 키는 `comment:<id>`. 답글 → 글쓴이 → 구독 순으로 수신자를 구하고, 동일 회원/event_key unique로 중복 제거합니다. 본인 활동은 제외합니다.
- 멘션은 문자열을 파싱해 수신자를 정하지 않습니다. UI에서 선택한 ID를 서버가 검색 허용·실제 계정·접근·양방향 차단 기준으로 검사합니다. 한 번에 5명, 작성자당 시간당 새 멘션 20건입니다. 동일 이벤트가 이미 있으면 알림을 추가하지 않습니다. 댓글이 수정되었다는 이유만으로 댓글 알림을 다시 만들지 않습니다.
- 검색 노출은 기본 꺼짐입니다. 동의한 닉네임·별도 공개 프로필만 검색하며 프로필에는 익명 글을 포함하지 않습니다. 일반 커뮤니티 응답에 익명 author_id를 추가하지 않습니다.
- 공지는 신규 생성 때만, 작성자를 제외해 알립니다. 중요도는 기존 owner_only를 사용하고 owner만 지정합니다. 공지별 알림 제외 가능, 수정 재발송 없음. 알림 있는 공지 신규 등록은 작성자당 시간당 3회입니다.
- 제재·해제·이의 제기 결과는 기존 governance의 필수 기록을 재사용합니다. 서버 시각으로 종료된 제재는 중복 없는 만료 통지를 생성합니다. 확인 시 또는 발송 작업에서 처리하므로 cron이 없으면 만료 즉시 백그라운드 통지는 보장하지 않습니다.
- 신고는 검토 중·완료·반려를 지원합니다. 신고자에게는 처리 상태와 일반 안내만 제공하며, 관리자의 내부 사유나 상대 회원 비공개 식별자는 제공하지 않습니다.
- 비활성 게시판·삭제 원본·차단 관계는 목록과 미읽음 개수에서 제외합니다. 푸시 전송 직전에도 접근·설정·세션·차단을 검사합니다.

## 알림 센터와 동기화

최신순 20개 페이지, 유형 아이콘·중요 표시·시각·개별 읽음/읽지 않음·전체 읽음·삭제·링크 이동을 제공합니다. 클릭 후 서버 읽음 처리가 성공해야 이동합니다. 삭제되거나 접근 불가한 원본으로 이동하면 기존 오류/재시도 화면을 표시합니다.

미읽음 개수는 서버 COUNT이며 임의 추정하지 않습니다. mutation마다 inbox_revision을 증가시켜 개수가 같아도 다른 기기의 읽음/삭제 변경을 감지합니다. 화면이 보이고 온라인인 동안 30초 간격, focus/online, 직접 새로고침 때 조회합니다. 요청을 합쳐 중복을 줄이고 숨겨진 탭은 폴링하지 않습니다. 지속 Realtime 연결을 추가하지 않았으며 즉시 실시간 동기화를 보장하지 않습니다. 작성 중인 화면은 알림 변경 때문에 다시 렌더링하지 않습니다.

제한 계정은 일반 V2 API와 알림 센터에 접근하지 않고 기존 계정 상태·이의 제기·민감 문의 경로로 운영 통지를 확인합니다. 이 예외를 일반 서비스로 확대하지 않습니다.

## 푸시 전송 정책

푸시는 계정의 push_enabled 기본 꺼짐 + 기기의 명시적 연결 + OS 허용이 모두 필요합니다. 차단된 권한에는 반복 요청하지 않습니다. 발송은 45초 지연으로 짧은 이벤트 묶음을 기다리고, 중요·운영 알림은 대기 지연을 줄입니다. 방해 금지는 중요 푸시에도 적용합니다. 내부 운영 통지는 그대로 남습니다.

서버 claim은 최대 25건·5분 lease, 기기당 동시에 한 작업만 claim, 성공 뒤 2분 내 이전 이벤트는 묶음으로 생략합니다. 여러 내부 기록은 보존하고 일반 푸시 하나로 안내합니다. 계정당 시간당 전송은 모든 기기를 합쳐 최대 20건입니다. 0(네트워크 오류)/429/5xx만 2분·10분 후 재시도하며 총 3회 한도입니다. 404/410은 기기를 비활성화하고 30일 뒤 발송 유지관리에서 삭제합니다. 만료된 lease는 재처리하고 7일 이상 밀린 작업은 실패 처리합니다. 완료 작업/시도 로그는 30일 뒤 발송 유지관리에서 정리합니다. 키·endpoint는 관리 통계에도 노출하지 않습니다.

외부 네트워크의 응답 유실 시 정확히 한 번 전달을 보장할 수는 없습니다. lease와 unique로 동시 중복을 막고 고정 notification tag로 OS 표시 중복을 완화합니다. 전송 결과 성공은 푸시 서버 접수이며 실제 OS 표시·사용자 열람과 다릅니다.

## 서버와 보안

push-dispatch는 서버 전용 발송 비밀로 만든 60초 HMAC 시각·nonce 서명을 검증하고, DB의 1회 nonce claim으로 재사용을 막습니다. 영구 비밀은 Vault/Edge에만 두며 pg_net 헤더에는 넣지 않습니다. 신뢰할 수 있는 서버의 수동 Bearer 인증도 상수 시간 비교로 검증합니다. Origin 있는 브라우저 호출은 거절하고 임의 수신자·내용을 입력으로 받지 않습니다. 일반 회원은 public.push_delivery에 EXECUTE 권한이 없습니다. service_role RPC와 서버 secrets는 프론트엔드에서 사용하지 않습니다.

Chrome/Firefox/Apple/Windows의 허용된 HTTPS 푸시 호스트만 저장·전송합니다. URL 자격 증명·다른 포트·유사 도메인·로컬 주소를 거절하고 redirect를 따르지 않습니다. VAPID 서명과 aes128gcm 암호화는 서버의 고정 버전 web-push로 생성합니다. 잠금 화면에는 고정 일반 안내만 표시하며 서버가 정한 내부 경로만 allowlist로 검증해 해당 화면으로 이동한 뒤 계정 권한으로 원본을 조회합니다. 잘못된 경로는 알림 센터로 보냅니다. 탈퇴·세션 삭제는 기기 및 연관 발송 데이터를 cascade 정리합니다.

## 검증과 남은 운영 확인

PGlite는 PostgreSQL 함수·권한·중복·세션·소유권을 실제 실행합니다. Hosted Supabase Auth/PostgREST/Edge 검증을 대신하지 않습니다. Deno는 디스패처 인증·SSRF·전송 실패 및 실제 암호화 요청 생성(외부 전송 없음)을 검사합니다. 원격 migration/Edge 적용, VAPID 설정, 주기 실행, 기기별 실제 수신·클릭·로그아웃 검증은 승인 후 수행해야 합니다.
