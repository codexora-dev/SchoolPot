## 역할 이관

기존 공지는 중요 여부를 추측하지 않고 모두 중요 공지로 보존한다. 최고 관리자가 검토 후 일반 공지로 변경할 수 있다. 기존 문의도 민감한 문의로 보호한다. 새 문의의 `기타 문의`와 사용자가 민감한 문의로 지정한 항목은 최고 관리자만 확인한다. 일반 문의에서 개인정보·계정 도용·보안·관리자 신고 등을 발견하면 이관 버튼으로 접근을 제한한다.

## 제재 적용과 해제

최고 관리자 대시보드의 **회원·제재 관리**에서 아이디·닉네임으로 검색하고 대상을 선택한다. 안내·경고, 1/3/7/30일, 7~30일 직접 지정, 30일 제한 후 영구 제한 검토, 영구 제한을 지원한다. 위반 규정과 구체적인 안내·처리 사유가 필수다. 안내·경고는 이용을 차단하지 않는다.

**30일 제한 + 영구 제한 검토**는 실제 30일 제한을 적용한다. 자동으로 영구 제한으로 바뀌지 않는다. 최고 관리자가 제재 기록과 이의 제기를 검토하고, 별도로 영구 제한을 적용할 때 `영구 제한` 확인 문구를 입력한다. 기간은 서버 시각 기준이며 기존에 더 긴 제한이 있으면 짧아지지 않는다. 기간 만료는 다음 서버 요청부터 효력을 잃는다. 해제는 사유와 최신 제한 버전을 비교한 뒤 해당 계정의 활성 제한을 해제한다.

부관리자는 **회원 제재 요청**에서 대상·위반 유형·규정·사유·제안 수준을 작성한다. 글·댓글·신고를 연결하면 서버에서 실제 대상 작성 자료인지 검사한다. 신고 화면에서 대상 검색으로 이동하면 신고·댓글 정보가 요청 작성에 연결된다. 요청은 접수 → 검토 중 → 승인/반려 또는 보완 요청으로 처리한다. 부관리자는 보완 후 재제출하거나 진행 중인 본인 요청을 취소할 수 있다. 승인은 요청 행 잠금·revision 비교·요청별 unique 제재로 중복 적용을 막는다. 최종 제재 수준과 사유는 최고 관리자가 확정한다.

새 요청은 최고 관리자에게, 결정은 요청자에게 사이트 알림으로 전달한다. 제재 대상 알림에는 다른 사람의 신고 내용이나 개인정보를 넣지 않는다. 대상 회원은 프로필의 **계정 상태·이의 제기**에서 자신의 안내·제재·답변을 확인한다.

## 이용 제한 화면

제한 상태로 로그인하거나 기존 세션의 제한을 확인하면 일반 사이트 화면을 계정 상태 팝업으로 교체한다. 닫기 버튼을 제공하지 않으며 Escape·주소 변경으로 서비스 화면에 진입할 수 없다. 서버에서도 커뮤니티·관리·학교 정보 API를 차단한다. 이의 제기, 본인의 이의 제기·민감 문의 답변 확인, 계정·개인정보 문의, 비밀번호 재확인을 거친 탈퇴, 로그아웃은 허용한다.

모든 관리자는 이의 제기를 읽고 답변할 수 있다. 답변이나 `종료` 상태만으로 이용 제한이 해제되지는 않는다. 최고 관리자가 회원·제재 관리에서 별도로 해제한다. 동일 제재에는 진행 중인 이의 제기 1건만 접수하며 접수 횟수를 제한한다.

차단 범위는 해당 로그인 계정이다. 로그아웃한 방문자에게 원래 공개된 팝업·게시판 이름·학급 설정·규정 같은 정보까지 숨기는 신원 추적 기능은 추가하지 않았다. 회원가입은 계속 재학생·실명·연령 인증 없이 진행한다. 새 계정으로 우회하는 사람을 실제 동일인이라고 식별한다고 주장하지 않는다.

## 역할·설정·정책

최고 관리자는 **관리자 권한**에서 부관리자를 임명·해임하고 사유·이력을 확인한다. 역할은 JWT나 클라이언트 입력이 아닌 DB를 매 요청마다 확인한다. 해임된 기존 로그인 세션도 즉시 관리 API를 호출할 수 없다. 화면은 포커스 복귀·접근 거부 응답·30초 주기로 변경을 확인한다. 변동 없는 확인과 비차단 안내는 작성 중인 입력을 초기화하지 않는다.

최고 관리자 승격·해임·탈퇴는 일반 역할 변경 UI에 포함하지 않는다. 마지막 최고 관리자 삭제·강등은 DB 트리거로 막고 최고 관리자 계정의 탈퇴 API는 별도 권한 이관 절차를 요구한다. 별도 이관은 현재 최고 관리자 확인, 새 최고 관리자 대상 확인, 운영 승인, 트랜잭션 안에서 최소 1명의 최고 관리자 유지, 감사 기록 및 기존 세션 재검증을 동반하는 운영 변경으로 진행한다.

서비스 설정은 표시 이름·학교 표시 이름·소개를 관리한다. 실제 NEIS 연결 대상은 검증된 학교 설정 파일을 따른다. 이용 규정은 최초 사용자 제공 요약·전문을 버전 1로 보존하며 요약과 전문을 함께 검토·확인하여 새 버전을 게시한다. 문구는 명령으로 실행하지 않는다. 공개 규정 화면은 서버 게시본을 읽고, 연결 실패 시에는 번들에 포함한 최초 원문으로 표시한다. 개인정보 정책·가입 화면의 기존 사용자 결정을 변경하지 않는다.

보안 운영 화면은 실제 DB의 private 테이블/RLS 수, 최고 관리자 수, 활성 제한 수와 서버 시각을 보여준다. Supabase Auth·네트워크 보안 설정을 가짜 스위치로 제어하지 않는다. 감사 기록에서 변경 사유와 전후 상태를 확인한다.

## 적용 순서와 남은 운영 검증

1. 사용자가 운영 DB 변경·역할 이관·배포를 승인했다. 아래 순서대로 적용·검증한다.
2. 역할 목록과 마이그레이션 상태를 다시 읽고 예상과 다르면 중단한다. 백업·복구 수단을 확인한다.
3. `20261113133531_admin_hierarchy_and_appeals.sql`을 Supabase migration으로 적용한다. 새 테이블 직접 접근 회수와 RLS, 함수 search_path·EXECUTE 권한을 확인한다. 기존 회원·작성 내용·소속·제한·공지·문의 건수를 비교한다.
4. 변경된 `delete-account/index.ts`, `handler.ts`, 기존 `_shared/http.ts`를 함께 Edge 함수로 배포한다. 최고 관리자 탈퇴가 로그아웃·삭제 전에 거절되는지 확인한다.
5. 승인된 변경을 main에 커밋·push하고 Pages 워크플로 완료 및 실제 빌드 식별자를 확인한다.
6. 실제 Auth/PostgREST로 owner/moderator/member 권한, 제한 계정의 서비스 거절·이의 제기·탈퇴 예외, 현재 세션의 해임, 중요 공지·민감 문의 권한, 새 요청·결정 알림을 검증한다. 사용자 계정에 임의의 제재·테스트 글을 만들지 않는다. 실제 제재 변형 검증에 필요한 전용 테스트 계정·정리 범위는 운영 승인에 맞춰 진행한다.

로컬 PGlite는 권한 SQL을 실행하지만 실제 Supabase Auth/PostgREST/Edge 또는 다중 DB 연결의 동시성 검증을 대신하지 않는다. production 적용 전 실패는 트랜잭션 롤백으로 중단한다. 적용 후 새 운영 기록을 버리는 자동 역마이그레이션은 제공하지 않는다. 문제 발생 시 기존 데이터를 보존하는 전진 수정 또는 검증된 백업 복구를 검토한다. DB 적용 전 신규 UI만 배포하지 않는다.
